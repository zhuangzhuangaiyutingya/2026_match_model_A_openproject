# 剩余优化空间分析（2026-09-23）

数据源：`results/leaderboard/baseline.json`（1200 格，官方评估器产出）。
本文件用于把下一轮优化精力导向收益最大的方向，避免重复试探已排除的路径。

## 一、Cache 不是当前瓶颈（已排除）

曾计划用"共享输入聚簇提升 L2 命中率"作为主攻方向（README 四条方向之一）。
实测与下界分析否定了这一判断：

- 400 个 P3 格中，DDR 带宽下界占 Makespan 比例 **>50% 的仅 5 格，>30% 的仅 25 格**；
- 全部 P3 格的跨核重复读潜力量约 1003 MB，其中 88% 集中在 120 格，
  但这些格的 Makespan 几乎由计算量决定，少读数据换不来时间；
- 实测 `case_067` P3 五核（重复读潜力 35 MB）：当前 12.59M cycles，
  其矩阵下界即约 12.2M cycles——即使重复读全部消除，收益也在 3% 以内。

结论：**Cache 高命中率是"锦上添花"，不是时间杠杆。**
`tensor 复用聚簇`类候选只有当某格 DDR 下界占比 >40% 时才值得尝试
（当前仅 c029/c012 等个位数格子）。

## 二、真正的瓶颈是 M/V 双维负载不均衡（主攻方向）

对 A<0.7 的 P3 格统计主导下界分量：

| 主导瓶颈 | 格数 |
|---|---:|
| PIPE_M 工作量 | 198 |
| PIPE_V 工作量 | 95 |
| 关键路径 CP | 7 |
| DDR 带宽 | 3 |

即 **293/303 个低完成度格由计算负载分配不均造成**，且集中在
"每个用例 12 格全低"的 23 个用例上：c095、c069、c005、c086、c068、
c008、c071、c088、c040、c009、c044、c084 等。

进一步对最差格做每核负载剖析，暴露两种不同的失效模式：

1. **负载严重倾斜**（如 c095 五核）：
   当前最优方案每核 max(M,V) = 0.98M / 0.02M ×4，
   最慢核是理想值的 4.58 倍——即 98% 计算压在一个核上。
   但 `wide_plan` 实测每核 M/V 已完美均衡（214K/203K ×5），
   说明现有候选集里的均衡方案被**其他代价**（spill 88MB、切分新增 75MB）
   抵消掉了：均衡后 DDR 流量折算约 147 万周期，几乎吃掉全部并行收益。

2. **工作集换入换出主导**（同上 c095）：
   每核活跃张量约 1.3MB，远超 640KB 片上容量（L1 512K + UB 128K），
   大窗口子图又拉长了张量生命周期，使 Belady 换出放大流量。

结论：**下一轮应在"均衡 + spill 控制"的联合目标上做搜索**，而不是只优化切边流量。

## 四、建议的下一步（按预期收益排序）

1. **P2/P3 的 spill 感知均衡**：目标函数改为
   `max(每核 max(M,V)) + λ·预估spill字节/60`，
   并在候选集中同时保留"均衡但高spill"与"轻微倾斜但低spill"两类方案；
2. **扩大小图/中图的均衡容差搜索档位**：c005/c086/c069 这类
   1.5K~6K 算子的图，12 格全在 A<0.2，说明现有档位完全没找到好解，
   值得对这批用例做参数网格加密（类似 v4/v5 对小图的做法）；
3. **P1 的 super-task 合并**（原计划项）：P1 每格独立 Task 的
   边界搬运与 100/1000 周期等待在低并行图上代价显著，
   但当前 P1 已有部分结构候选收益，优先级低于第 1、2 项。

## 五、小图（<1500 算子）的新发现：跨核延迟主导（2026-09-24）

对 c064/c071/c026 等小图的诊断显示第三种失效模式，与前述两类都不同：

- c064 P3 四核：makepan=17,880，但下界仅 max(M/k,V/k,CP,DDR)=3,934；
- 同图**单核** makespan≈18,000，即单核已达自身下界的 0.87，
  而四核仅达四核下界的 0.22；
- 同时 spill=0、切分新增搬运=0（v10~v14 网格已把这两项压到零）。

结论：**小图的多核收益被跨核通信延迟吃掉**。这类图算子极小
（c064 最大单算子仅 108 周期）、层宽大、跨核边多，每条跨核边
在场景 B 需付 COPY_OUT+COPY_IN+500 周期同步延迟，其量级远超算子本身。

由此推出小图的正确策略方向（尚未实现）：
1. **按"跨核边延迟预算"切分**：目标函数加入 `跨核边数 × 500`，
   而不是只算字节；字节少但条数多的切分同样致命；
2. **优先减少跨核边条数**：把同一依赖链尽量留在一核，
   宁可轻微不均（这些图计算量小，不均的代价低于延迟）；
3. **小图核数自适应**：当 `总计算量 < 跨核边数×500` 时，少用核是正确的，
   当前候选集虽有 grow_half 档，但触发条件（par<1.5k）不覆盖此情形；
   建议新增判据：`W_total/k < 每核跨核边数×500` 时禁用 k 核方案。

## 六、已否决：P1 同核子图合并（2026-09-24）

设想：场景 A 下每个子图是独立 Task，同核相邻子图仍需边界 COPY + 100 周期
等待；把同核子图合并为一个 Task 可同时消除两者。

实测否决，两点原因：
1. **性能反降**：c001 k2 166,034→247,188（-33%）、c044 k2
   96,543→154,407（-38%）。合并后单 Task 工作集变大，spill 显著增加
   （c044 新增搬运 0.2MB→4.4MB），抵消并超过省下的边界开销；
   仅 c026 k2 微增 0.8%。
2. **可能非法**：交叉依赖顺序会使合并后的子图图成环
   （c095 k2 直接被官方评估器拒绝），因此该变换不能作为通用后处理。

结论：P1 的边界开销应通过**切分本身**（更少的子图/更粗粒度，
即现有 mult 档位）来控制，而不是事后合并同核子图。

## 八、P3 Cache 收益为何低：量化与机制（2026-09-24）

**量化**（400 个 P3 格）：
- 完美缓存的理论收益上限（重复读字节 × (1/60 − 1/250) / makespan）：
  **平均 +6.10%、中位 +3.01%，156 格空间 >5%**，最高 c080 k4 达 +58.6%；
- 当前实际捕获：**平均 +1.05%**（约理论空间的 1/6）。

**已测试的捕获手段与结果**：
| 手段 | 结果 |
|---|---|
| 输入亲和分核（cache_affine，weak/strong 两档 × 容差 0/0.25/0.5） | **全部更差**：c044 k4 107K vs 现状 67K、c046 139K vs 78K、c037 k5 93K vs 43K——牺牲均衡的代价远超缓存收益 |
| 结构性减少重复读（把同输入消费者聚到同核） | 同上，等价于亲和方案 |
| 现有候选（grow/count/mv/level/wide/wave） | 已覆盖，捕获率仅 1/6 |

**机制判断**：命中率低（全表 9%~17%，c044/c046 仅 0.0%~0.7%）的根因是
**1MB FIFO 在两次读取之间被中间流量换空**——而中间流量的主要成分正是
核内 spill（换入换出）与跨核边界拷贝。即：**缓存收益被 spill 流量吃掉了**。
因此提升 Cache 收益的正确前置是降低 spill（见第二节），而不是调度亲和。

**旁证**：c080/c037/c011 等命中率较高的格（0.48/0.64/0.61），其
spill 也相对更少；反之 c044/c046 命中率≈0。


## 九、v31：region_grow 链图前沿耗尽缺陷（根因修复，P1 最大单项收益）

**现象**：92 个 P1 格（23%）在图并行度远超核数时 S≈1.00（case_020
par=157 全核数 S=1.00；case_045/049/056/050/047 等同）。这些格的
最优方案是单核兜底——所有多核候选全部输给单核。

**根因**（case_020 实测）：图由 ~292 条弱连通链组成（avg_succs=1.15）。
region_grow 从种子沿链生长，**一条链长完堆即空**，`while ... and heap`
把"前沿耗尽"当成"簇已满"，每个簇只装下 1 条链（2128/532608 工作量），
**98%~99% 算子落入兜底散射**：既摧毁均衡（单核吞 95% 工作），又把
张量撕成 20~34MB 跨核拷贝（60B/cyc 下 ≈ 全图工作量），多核必然劣于单核。
stall 普查：**100/100 用例都发生前沿耗尽**（35~3273 次），只是多数图
连通度足够高、散射占比小而已。

**修复**：前沿耗尽且未达目标额时**换新种子继续装填本簇**（reseed）。
case_020 P1 k5：532,746 → 123,875（S 1.00→4.30，smoke 实测 v31_grow_m8）；
case_045 P1 k5：S 2.39→3.62；case_020/045 全部 16 格 P1/P2 大幅获胜。
全表 scattered=0（兜底散射在所有用例上消失）。

**注意：并非全面占优**。本地 576 格对照：链图（case_020/045）碾压级
改善；但 case_011/027 的部分格旧散射+精化反而更好（case_011 P1 k3：
旧 67,244 vs 新 89,480）。故两种行为**并列保留**：
- `grow/grow_count/grow_mv`：reseed=True（新默认，链图主收益）；
- `grow_ns/grow_count_ns/grow_mv_ns`：reseed=False（旧行为，
  candidates_for 已加入 growns_m2/m4[_t10]）。
榜单按 min-makespan 合并，两族并存无回归风险。

**回归防护**：tests/test_region_grow_reseed.py（链图均衡/无散射/
孤立算子终止/grow_ns 旧行为 4 组断言）。

**spill 因果验证（第八节后续）**：spill 重格上 BEST 方案 4/5 已零
spill 且比 grow 变体好 1.4~2.8 倍——"细粒度→少 spill→高命中→低
makespan"因果链**不成立**；分区质量（均衡+连通）才是主因，与本次
根因一致。case_046（hit=0.638）与 case_044（hit=0.003）切分流量
相同、命中率天差地别，说明命中率由切张量的复用时序决定，非流量。

## 十、v32：bandcomp 深度窗口×连通分量条带（第二轮根因级修复，+703格）

**现象延续**：v31 补种修复后仍有 68 个 P1 格 S≈1.0（case_005/049/050/
056/047 等 ~23 例深而稀疏图，depth 138~460、层内大量弱连通分量）。

**根因二**：这些图上补种生长的簇是"多生长岛并集"，任务图交错成环
（case_005 p5 双向 48 字节边×4 对，实测 acyclic=False）。任务图有环
即非法，`_partition_safe` 只能回退横切——横切按深度分层天然串行，
S≈1.0。旧行为（散射兜底）同样成环。**修环**（搬边界算子）在深交错
图上不收敛，且对退化输入会塌缩成单簇（已加簇数护栏）。

**bandcomp**：按深度切窗口（w 层/窗），窗内取弱连通分量——分量间
互无边（定义保证），窗口间边只会从浅指向深 ⇒ **任务图天然无环**。
分量按 max(M,V) LPT 装核，带前驱粘性（优先跟随前驱分量所在核，
减少跨核 1000 周期等待）。

**关键权衡**：窗口越小并行度越高，但窗口边界的切分流量越大
（case_005 w4 切 3.3MB vs w24 切 0.9MB）。实测甜点 w=10~16。

**全量结果**（400 任务，w∈{4,6,10,16}）：**703 格改进**。
代表：case_003 P1 四核 +105%（482K→235K）、case_049 P1 五核
S 1.00→2.00、case_005 P1 五核 S 1.02→1.40、case_056 -41%。
官方指标（v29→v32）：P1 2.982→3.429（五核）、P2 3.435→4.051、
P3 3.498→4.138。v31+v32 两轮合计 +987/1200 格。

**未尽**：窗口 w 只扫了 4 档；粘性系数 0.5 固定；分量内未再细分。
甜点附近（w8/12/20）与粘性调参仍有空间。

**P1 super-task 链合并（bandcomp 后处理）——负结果**：把同核相邻窗口
分量贪心合并（无环才并），实测 case_005/069 makespan 反升 20~40%
（跨核等待节省被"中间结果拖到合并 Task 尾部"的假等待吃掉）、
case_044 触发官方评估器环报错（_task_graph_ok 与官方收缩图判定存在
口径差）。case_071 单例收益（18.8K vs 20K）不具普适性，放弃该方向。

## 十一、v36：全量交叉评估（零成本收割，+59格）

方案格式（node_to_subgraph + core_schedules）跨问题通用，因此每个
问题的赢家方案可以直接在其他问题的官方评估器下重评。sync_cross_v36.py
覆盖 6 方向 × 400 格 = 2400 次评估（服务器 37 分钟）：74 个候选、
采纳 59 格。P1 获益最大——P1 弱格 case_009/020/063/086 等直接采用
P2 赢家方案（bandcomp 族在场景 B 代价下长出的分区，在场景 A 下依然
占优）。此前只做过 P3←P2 单向同步（sync_p3_from_p2），其余 5 个方向
是本节补齐的免费空间。

教训（工程）：远程长跑脚本上线前先验证环境（目录存在性）与
排序稳定性（同 key 多来源去重）；本次因这两点各浪费一轮 37 分钟。

**六轮累计（v29→v36）**：P1 五核 2.982→3.558、P2 五核 3.435→4.223、
P3 五核 3.498→4.327，合计 +1967/1200 格。v36 后剩余弱格 15 个
（case_005/044/056/064/069/071/083/086/088 的 P1），均为链间耦合强
或 fork-join 归约等待的结构性缺口。
